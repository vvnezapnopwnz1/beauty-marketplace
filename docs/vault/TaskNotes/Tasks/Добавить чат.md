## TL;DR

Идея распадается на три уже спланированные фазы. Phase 1 (внешний чат гость↔мастер на привязанной записи) — **закрыта** (см. `product/status.md` от 2026-05-07 follow-up). Подзадачи в этом тикете — это Phase 2A и 2B из [`product/chat-roadmap.md`](../../product/chat-roadmap.md). Floating-CTA «красный блок справа внизу» — это уже существующая `features/chat-window/ChatTrigger`, она dead-mounted и ждёт unread-counter (Phase 2C).

## Что уже работает (Phase 1)

- Чат привязан к `appointment_id`, доступен:
  - гостю по `access_token` через `/chat/:accessToken` и embed в `entities/user-appointment/AppointmentCard` на `/me`;
  - управленцам и мастеру — внутри `AppointmentDrawer` дашборда салона и в `MasterPersonalAppointmentDrawer`.
- Анти-спам: правило «первого шага» (гость пишет 1 сообщение, дальше отвечает мастер).
- Маскировка контактов (телефоны RU + мессенджеры) на storage-level.
- Архивация чата через 24ч после `completed`.
- SSE-доставка через `chat.message`; гость подписан на `/api/v1/chat/external/rooms/{token}/stream`.
- Mobile: route `/chat/[appointmentId]`, deep-link push'ей.

## Подзадачи из изначальной формулировки

### A. Чат «между мастером и управленцами салона» (обсуждение записей)

→ Это **Phase 2B (internal chat)** в roadmap. Привязка к `salon_id`, не к записи; общий канал салона + личные диалоги owner/receptionist ↔ мастер. Системные сообщения от триггеров (DnD-перенос, смена статуса, no-show).

**Что нужно дополнительно решить:**
- Уведомление мастера при системном событии — переиспользовать `AppointmentChatHook` или новый `SalonChatHook`?
- Видимость: мастер видит только свои треды + общий канал; админ/owner видит всё.
- Threading: ветки на запись внутри internal-чата vs полностью отдельный канал.

### B. Чат «между гостями и мастерами о записях» (без привязки к записи)

→ Это **Phase 2A («Задать вопрос», pre-booking inquiry)** в roadmap. Кнопка «Задать вопрос» рядом с «Записаться» на странице салона/мастера.

**Что нужно дополнительно решить:**
- Гость без записи → как создавать `chat_room`? Скорее всего новый `type='inquiry'` с `salon_id` (или `master_profile_id`) + временный `access_token` гостя.
- Эскалация: первое сообщение → owner/receptionist, через N мин без ответа → мастер (или сразу мастеру с copy в общий канал?).
- Фото в первом сообщении (требует object storage — см. `product/backlog.md` про S3/MinIO; одна и та же инфра, что под аватары).
- Quick replies: шаблоны на стороне мастера/салона (мини-CMS в кабинете).
- «Сформировать запись» — кнопка трансформации диалога в `appointment` + системное сообщение клиенту.
- Анти-увод: уже работает маскировка контактов; добавить флаг подозрительной активности (3+ inquiry без записи) для модерации.

### C. UI — floating CTA «красный блок fixed справа внизу»

- Компонент уже есть: `frontend/src/features/chat-window/ui/ChatTrigger.tsx`, но не смонтирован — нужен либо unread-count из бэкенда, либо клиентская approxima­ция (Phase 2C).
- На странице `/me` чат уже встроен в карточку записи (collapsible) — там CTA не нужен.
- На странице салона/мастера CTA имеет смысл только под Phase 2A («Задать вопрос»), иначе кнопка будет dead, пока нет активной записи.

### D. Заметка пользователя про «гость → одно сообщение → дальше диалог»

✅ Уже реализовано в Phase 1 (правило «первого шага» в `chat_service.go`, см. `product/status.md` 2026-05-07). Для Phase 2A то же правило надо явно скопировать на `type='inquiry'`-комнаты.

## Зависимости

1. **S3/MinIO storage** (см. `product/backlog.md` → «Загрузка аватара пользователя») — блокирует фото-чат в 2A. Поднимать одновременно с аватарами и фото салона.
2. **Тестовая инфраструктура** (vitest+RTL+MSW для frontend, jest-expo+RNTL для mobile) — без неё Phase 2 идёт без safety-net, регрессии в чате очень дорогие. См. Phase 2C в roadmap.
3. **Unread counter** — нужен для смонтирования `ChatTrigger`. Backend extension `unreadCount` к `getRoomForAppointment` + общий счётчик по пользователю в `me`.
